## 6475为什么现在没有自动变锁

6475（ba_mako1_0030_0010_0000_cld_0，旧run209）是旧流程保存的原稿候选“ 不痛不痒 ”。旧判定是在保守裁边后仍超长，于是后续改稿；不会因为新代码上线就重新处理并锁定历史音频。按钮算法能挽救，意味着它是可优先重处理的输入，不代表已经重新核过新字节并满足锁定条件。

新DSP链路已经具备真按钮整句对齐、按“发”缩放、实际新文件核字/SHA和原稿锁条件；缺少的是“在同一新run优先复制复用已有原稿候选”的受控执行入口。不能直接改6475的旧status/核字metadata，也不能因为旧ASR通过就移给对齐后的新字节。当前本轮不运行这一步。

## 最小后续接入方案（待审阅，不已上线）

1. 普通任务内先筛同stem、ready、candidate、完整spoken正文与当前原稿及game_zh快照一致的WAV。无锁/异常，字幕不含不同正文；不因父子分组把原稿子候选漏掉。忽略旧ASR“通过/未过”作为准入证明，所有新字节都要重新核字。`casual-original-reuse-policy.ts`目前只做此只读判定。
2. 以后由同一auto-run受控意图导入独立副本，不额外造多个run。锁台词→新run→人工标记→源版本，读取实际源SHA/字幕与准备时一致，再复制bytes并保存source_id/source_run_id/源SHA。metadata清空新副本核字结论，不把旧duration_review伪装成新结论；不修改旧auto_run_id、review_state、父子归属或字幕。
3. 新副本调用同一候选DSP/核字/发声缩放/最终提交函数；通过则原稿锁，否则保留新历史，再按已确认规则决定是否进入新TTS。复制/编辑不占原生TTS次数；核字仍有真实成本，不静默开跑。
4. 有cleanup时只接受能够闭合证明旧JP保留段/正文位置、源SHA和完整字幕的提取方案；仅凭spoken看起来像原稿不足以把旧正文半成品当全文。首版可明确记“不安全复用，需原稿新制作”，而非编造成功证据。
5. 匿名生成需独立迁移 `line_tts_versions.speaker DROP NOT NULL`（保留FK、NULL自然不绑定某人物）。只为已验证自动任务开放当前stem的JP/其可信处理参考，不允许匿名任选旁人参考；不建unknown假人物。手动/场景额外权限另行审阅。
6. 译文准备单列来源审计，状态done和源hash格式/计算方式须与真实翻译生产者一致。锁内只更新仍空的text_zh，记录语言、原文、源hash、译文hash、模型、时间与采纳意图；并发人工填字优先。不能仅凭translate_zh_jp/en列非空就执行。

本轮不新增 `/auto-run`选项或自动采纳/匿名生成权限，不执行schema变更，不写任何业务数据或锁。调试台账须把未实现/技术缺口标pending，不能把纯判定通过写成制作成功。
